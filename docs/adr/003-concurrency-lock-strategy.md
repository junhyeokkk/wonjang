# ADR-003: 동시 전표 입력은 설계로 경합을 없애고, 락은 마감 경계에만 건다

- 날짜: 2026-10-19
- 상태: 제안됨 (4·5주차 동시성 테스트 후 승인)

## 맥락 (Context)

같은 계정에 동시에 전표가 들어오면 잔액·채번이 꼬일 수 있다. 또 일마감(스냅샷 생성) 도중
마감일 이전 날짜로 전표가 들어오면 스냅샷이 틀어진다.

## 검토한 선택지 (Options)

1. **비관적 락** — 전표 입력 시 계정 행을 `SELECT ... FOR UPDATE`. 같은 계정 입력이 전부 직렬화된다.
2. **낙관적 락** — `@Version` + 충돌 시 재시도. 잔액 컬럼이 있어야 의미가 있다.
3. **락 없음 (설계로 경합 제거)** — 잔액을 행에 저장하지 않으므로 분개 INSERT끼리는 갱신할
   공유 행이 없다.

## 결정 (Decision)

**기본은 3번.** 잔액은 파생 데이터(절대 원칙 #5)라 전표 입력끼리는 경합하지 않는다.
락이 필요한 두 지점만 따로 처리한다.

| 지점 | 문제 | 처리 |
|------|------|------|
| 전표 채번 `voucher_no` | 동시 요청이 같은 번호를 만들 수 있음 | DB 시퀀스 `voucher_no_seq` (락 없음) |
| 마감 ↔ 전표 입력 | 마감 중 마감일 이전 전표 유입 | 단일 행 `ledger_state(closed_through)` 행 락 |

마감 경계 처리:

- 전표 입력: `SELECT closed_through FROM ledger_state WHERE id = 1 FOR SHARE` 후
  `voucher_date > closed_through` 검사. **FOR SHARE끼리는 서로 막지 않으므로** 입력 동시성은 유지된다.
- 일마감: 같은 행을 `FOR UPDATE`로 잡고 스냅샷 생성 → `closed_through` 갱신 → `closings` 이력 기록.
  진행 중인 입력이 끝나길 기다리고, 마감 중에는 새 입력이 대기한다.

## 결과 (Consequences)

- 얻는 것: "락이 필요한 곳에만". 평상시 입력은 락 경합 0.
- 트레이드오프: 마감이 실행되는 동안 전표 입력이 잠깐 대기한다. 마감은 하루 1회라 허용.
  시퀀스는 롤백돼도 번호가 소비되므로 voucher_no에 **구멍이 생길 수 있다** (연속성 보장 안 함).
- 대안: `pg_advisory_xact_lock_shared` / `pg_advisory_xact_lock`으로 같은 효과를 낼 수 있다.
  행 락은 잠금 대상이 스키마에 드러나 설명하기 쉬워서 택했다.
- 검증: AC-24 (100 스레드 × 10회, 시산표 균형·voucher_no 중복 0), 마감 동시 실행 테스트.
  실패하면 이 ADR을 다시 쓴다.
