# ADR-001: entries는 append-only로 두고, 정정은 역분개로만 한다

- 날짜: 2026-10-19
- 상태: 승인됨

## 맥락 (Context)

분개(entry)를 수정할 수 있게 하면 "언제 얼마였는지" 이력이 사라진다. 금융 원장은
감사 추적이 필수이고, 한 번 기록된 돈의 이동은 사후에 바뀌면 안 된다.

## 검토한 선택지 (Options)

1. **UPDATE 허용 + 별도 이력 테이블(audit log)** — 익숙한 방식이지만, 이력을 남기지
   않는 코드 경로가 하나라도 생기면 이력이 빠진다.
2. **소프트 딜리트(`deleted_at`)** — 행은 남지만 "삭제됨" 플래그 하나로 원장 의미가
   바뀐다. 모든 조회에 필터가 붙고 누락 시 잔액이 틀린다.
3. **UPDATE/DELETE 금지, 정정은 역분개 전표로만** — 원장 자체가 이력이 된다.

## 결정 (Decision)

**3번.** DB 트리거(`trg_entries_immutable`, [V3](../../src/main/resources/db/migration/V3__triggers.sql))로
entries의 UPDATE/DELETE를 거부한다. 애플리케이션에도 entries를 수정·삭제하는 코드와
API(`PUT /entries` 등)를 두지 않는다.

정정은 `POST /vouchers/{id}/reverse`로 차변↔대변을 반전한 새 전표를 추가해 처리한다.

- 역분개 전표는 `reverses_voucher_id`로 원본을 가리킨다. UNIQUE 제약으로 한 전표는
  한 번만 역분개된다 (AC-15).
- 역분개 전표 자체는 다시 역분개할 수 없다. 원본을 되살리려면 새 전표를 입력한다.
- 역분개 일자는 기본값이 요청일이며, 마감일 이후여야 한다 (원본이 마감 기간에 있어도
  역분개는 열린 기간에 기록된다).

## 결과 (Consequences)

- 얻는 것: 별도 이력 장치 없이 원장이 곧 감사 기록. 앱을 우회한 SQL도 DB가 막는다.
- 트레이드오프: 오타 하나를 고쳐도 전표가 2개 늘어난다(역분개 + 재입력). 원장이
  길어지는 문제는 일마감 스냅샷([ADR-004](004-balance-snapshot.md))으로 보완한다.
- 재검토 조건: 없음. 이 프로젝트의 핵심 전제다.
